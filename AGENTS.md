# AGENTS.md

## Проект

Клиентское приложение для пошагового создания D&D-персонажа. Стек: React 19, TypeScript, Vite, React Router, Material UI (MUI) и Sass. Интерфейс и доменные данные преимущественно на русском языке.

## Команды

Используйте `npm`: в репозитории есть `package-lock.json`.

```bash
npm ci          # установить зависимости с точными версиями
npm run dev     # запустить Vite в режиме разработки
npm run lint    # проверить ESLint
npm run build   # выполнить проверку TypeScript и production-сборку
npm run preview # посмотреть production-сборку локально
```

Перед передачей изменений выполните как минимум `npm run lint` и `npm run build`. Автоматизированных тестов в проекте пока нет; для изменений UI также пройдите затронутый шаг мастера в браузере.

## Структура

- `src/main.tsx` — точка входа приложения.
- `src/routes.tsx` — маршруты; новые страницы регистрируйте здесь.
- `src/pages/` — страницы и их локальные компоненты. Мастер расположен в `pages/create-character/`.
- `src/pages/create-character/ui/` — независимые шаги и компоненты мастера. Держите код шага рядом с его UI, хуками и утилитами.
- `src/api/` — типы API, запросы и общий HTTP-клиент. Не выполняйте `fetch` напрямую из компонентов, если для сущности уже есть модуль API.
- `src/assets/` и `public/` — статические ресурсы.
- `src/theme.tsx` — общая MUI-тема; общие визуальные токены добавляйте туда, а не дублируйте в компонентах.

## Правила разработки

- Пишите компоненты на TypeScript и явно описывайте их `Props`; для импортов, используемых только в типах, применяйте `import type`.
- Сохраняйте существующий стиль в изменяемом файле. В коде встречаются двойные и одинарные кавычки; не форматируйте несвязанные файлы ради единообразия.
- Используйте функциональные компоненты и React hooks. Не меняйте состояние напрямую; передавайте обновления наверх через существующие callback-props.
- Для вёрстки предпочитайте MUI-компоненты и `sx`. Локальные стили размещайте в `.module.scss`; не добавляйте глобальные CSS-правила без необходимости.
- Строки интерфейса добавляйте в корректной UTF-8 кодировке и на русском, следуя окружающему тексту. Не копируйте отображаемую в терминале mojibake-последовательность `Р...` — это артефакт кодировки консоли.
- При изменении шагов мастера сохраняйте его инварианты: нельзя перейти вперёд без обязательного выбора; изменение класса должно корректно обновлять зависимые характеристики; экран загрузки и ошибки API должны оставаться обработанными.
- Не ослабляйте TypeScript или ESLint (например, глобальным отключением правил) ради прохождения проверки. Локальное подавление допустимо только с кратким объяснением, почему типизировать код невозможно.

## Работа с API

- Базовый адрес определён в `src/api/apiClient.ts`: `http://localhost:5000/api`. Для полноценной ручной проверки требуется локальный backend на порту 5000.
- Описывайте новые ответы API типами в `src/api/` и экспортируйте их через соответствующие публичные модули.
- Сохраняйте обработку состояний `loading` и `error` через существующий `useFetch` или эквивалентный явный механизм.
- Не добавляйте в клиент секреты, токены или персональные данные. Если адрес API станет конфигурируемым, используйте переменные Vite с префиксом `VITE_`.

## MongoDB и каталог D&D

- Локальный MongoDB-сервер доступен на `127.0.0.1:27017`. Рабочая база приложения — `dnd_su`; frontend по-прежнему должен обращаться к ней только через backend API на порту 5000.
- `dnd_su` — справочный каталог D&D из 15 коллекций: `abilities`, `alignments`, `armors`, `backgrounds`, `classes`, `equipment`, `equipmentpacks`, `feats`, `items`, `languages`, `races`, `skills`, `spells`, `tools` и `weapons`.
- Допустимый внешний справочник для правил D&D 5 редакции — [5e14.dnd.su](https://5e14.dnd.su/): там есть классы, расы, предыстории, черты, заклинания и предметы. Перед переносом сведений сверяйте редакцию и первоисточник, а для объёмных текстов и изображений соблюдайте условия использования сайта и авторские права.
- Для исследования схемы применяйте MongoDB MCP Server с `--readOnly`; не используйте его для модификации данных. Строку подключения и учётные данные не записывайте в репозиторий, `.env` или `AGENTS.md`.
- Снимок на 2026-07-26: крупнейшие коллекции — `spells` (2 200 документов), `items` (902), `equipment` (136), `races` (50), `feats` (38), `weapons` (37), `tools` (30); `equipmentpacks` пуста. Перед добавлением миграций или предположений о данных перепроверяйте фактические количества и схему.
- Не предполагайте соответствие REST-маршрута и имени Mongo-коллекции: `/items` в текущем API вернул 136 записей, хотя в MongoDB `items` содержит 902, а `equipment` — 136. Сначала уточняйте контракт backend-маршрута.
- В `items` встречаются поля вне TypeScript-интерфейса из `src/api/items.ts`; нормализуйте и валидируйте ответ на стороне backend, а не расширяйте UI под произвольные поля.
- MCP не вернул объявленных дополнительных индексов для этих коллекций. При появлении фильтрации по названию, классу, уровню или типу урона сначала измерьте запросы и добавляйте индексы в backend-миграции, а не в клиентском коде.

## Границы изменений

- Не редактируйте сгенерированные каталоги `node_modules/` и `dist/`.
- Не меняйте зависимости, lock-файлы, конфигурацию Vite/TypeScript/ESLint без прямой необходимости для задачи.
- В репозитории присутствуют и `package-lock.json`, и `yarn.lock`; не обновляйте оба. Для обычной работы и изменений зависимостей используйте npm и обновляйте только `package-lock.json`, если это действительно нужно.
- Делайте минимальные, тематически связанные изменения и не удаляйте существующую функциональность без явного требования.

## Проверка изменений

1. Запустите `npm run lint`.
2. Запустите `npm run build`.
3. Для UI вручную проверьте адаптивность, клавиатурную доступность, видимые состояния загрузки/ошибки и переходы между шагами.
4. В итоговом сообщении перечислите изменённые файлы, выполненные проверки и известные ограничения (например, недоступный backend).
